# 09 上下文工程详解

## 9.1 什么是上下文工程

上下文工程 (Context Engineering) 是指**精心设计和管理输入给 LLM 的上下文内容**，以最大化模型的输出质量和效率。

核心理念：不是把所有信息都塞进上下文窗口，而是**有意识地选择、组织和管理**进入上下文的内容。

---

## 9.2 为什么上下文工程重要

### 9.2.1 上下文腐蚀 (Context Rot)

**现象**：随着上下文窗口中的 tokens 增加，模型从上下文中准确回忆信息的能力反而会**下降**。

类似于"大海捞针"(needle-in-a-haystack) 测试所揭示的问题。

**简单比喻**：
- 短上下文 = 小房间里找东西 → 一眼就能看到
- 长上下文 = 大仓库里找东西 → 东西越多，找特定物品越费劲

### 9.2.2 注意力预算

LLM 的注意力是**有限资源**，就像人类的工作记忆有限一样。

**原因**：
1. **注意力稀释** — Transformer 架构让每个 token 与上下文中所有 token 建立 O(n²) 级别的注意力关系，信息量大了，重要信息容易被"淹没"
2. **位置感模糊** — 上下文越长，模型对"哪个信息在哪里"的定位精度会下降
3. **检索精度下降** — 类似人在信息过载时会"记不清细节"

### 9.2.3 性能梯度

模型在长上下文中依旧能工作，但在**较短、精炼的上下文**中，信息检索与长程推理的精度会更高。

---

## 9.3 上下文工程的核心策略

| 策略 | 说明 |
|------|------|
| **筛选** | 只放入真正相关的信息，过滤噪音 |
| **压缩** | 用更少的 token 表达同样的信息（如摘要、结构化格式） |
| **排序** | 把重要信息放在更容易被"注意到"的位置（通常是开头或结尾） |
| **分块** | 长任务拆成多轮，每轮只处理必要的上下文 |
| **检索** | 用 RAG 等技术动态拉取相关内容，而不是一次性全塞进去 |

上下文工程不只是"精炼"，更像是**上下文的架构设计** — 决定什么进、什么不进、怎么组织、什么时候进。

## 9.4 Hello-Agents 中的实践：ContextBuilder

### 9.4.1 GSSC 流水线设计

ContextBuilder 实现了 **Gather-Select-Structure-Compress** 四阶段流水线，将上下文工程理论落地为可执行代码。

#### 核心数据流

```
用户问题 + 历史 + 指令
    ↓
1. Gather:   多源信息 → ContextPacket[]
    ↓
2. Select:   ContextPacket[] → 筛选 + 评分 → 高价值子集
    ↓
3. Structure: 高价值子集 → 分区模板 → 结构化文本
    ↓
4. Compress: 结构化文本 → 预算守护 → 最终 prompt
```

#### 阶段重要性分层

| 阶段 | 重要性 | 作用 |
|------|--------|------|
| **Gather** | 核心 | 决定信息来源的广度（Memory/RAG/History） |
| **Select** | 核心 | 决定信息质量（评分 + 预算控制） |
| **Structure** | 后处理 | 格式化排版（6区模板） |
| **Compress** | 后处理 | 简单截断（未来可用 LLM 摘要） |

**80% 的价值在 Gather 和 Select**。

### 9.4.2 Gather 阶段：多源收集

按优先级（P0-P3）从 4 个数据源收集候选信息：

```python
# P0: 系统指令（强约束，必须保留）
if system_instructions:
    packets.append(ContextPacket(
        content=system_instructions,
        metadata={"type": "instructions"}
    ))

# P1: 记忆（任务状态 + 相关记忆）
# 1) 搜索任务状态 - 恢复长期任务上下文
state_results = memory_tool.execute(
    query="(任务状态 OR 子目标 OR 结论 OR 阻塞)",
    min_importance=0.7
)

# 2) 搜索相关记忆 - 检索历史经验
related_results = memory_tool.execute(query=user_query)

# P2: RAG（知识库检索）
rag_results = rag_tool.run({"action": "search", "query": user_query})

# P3: 对话历史（最近10条）
recent_history = conversation_history[-10:]
```

**设计要点**：
- 容错性：每个数据源用 try-except 包裹
- 元数据标记：每个包都有 type 字段
- 广撒网：不考虑预算，先收集所有可能相关的信息

### 9.4.3 Select 阶段：评分筛选

#### 评分公式

```python
# 1. 相关性（关键词重叠）
relevance = len(query_tokens ∩ content_tokens) / len(query_tokens)

# 2. 新近性（指数衰减）
recency = e^(-Δt / τ)  # τ = 3600秒（1小时）

# 3. 复合分
score = 0.7 × relevance + 0.3 × recency
```

#### 筛选流程

```python
# 1) 计算相关性和新近性
# 2) 计算复合分
# 3) 分离系统指令（固定纳入）
# 4) 过滤低质量（relevance < 0.3）
# 5) 按预算贪心填充
for p in sorted_packets:
    if used_tokens + p.token_count <= available_tokens:
        selected.append(p)
        used_tokens += p.token_count
```

**设计要点**：
- 多维评分：相关性 + 新近性
- 系统指令优先：不参与评分竞争
- 预算守护：贪心算法控制总 token 数

### 9.4.4 Structure 阶段：6区模板

将筛选后的信息包组织成固定的分区模板：

```
[Role & Policies]  ← P0: 系统指令
你是代码助手，必须用 Python 回答

[Task]             ← 用户问题
用户问题：优化登录性能

[State]            ← P1: 任务状态
关键进展与未决问题：
【任务状态】正在重构 auth 模块
【阻塞】Redis 连接配置待确认

[Evidence]         ← P2: 事实证据
事实与引用：
【历史经验】上次讨论过使用 JWT token
【知识库】API文档：login 接口支持缓存

[Context]          ← P3: 对话历史
对话历史与背景：
[user] 优化登录
[assistant] 可以加缓存

[Output]           ← 输出约束
请按以下格式回答：
1. 结论（简洁明确）
2. 依据（列出支撑证据及来源）
```

**设计要点**：
- 结构清晰：6个区域语义明确
- 便于定位：LLM 可快速找到需要的信息
- 灵活可选：某些区域可以为空

### 9.4.5 Compress 阶段：预算守护

```python
current_tokens = count_tokens(context)
available_tokens = config.get_available_tokens()  # 例如 6800

if current_tokens > available_tokens:
    # 按行截断，保留完整段落
    for line in lines:
        if used_tokens + line_tokens <= available_tokens:
            compressed_lines.append(line)
```

**当前实现**：简单截断（后处理）  
**未来改进**：LLM 摘要（变成核心阶段）

### 9.4.6 配置参数

```python
class ContextConfig:
    max_tokens: int = 8000           # 总预算
    reserve_ratio: float = 0.15      # 为输出预留 15%
    min_relevance: float = 0.3       # 最小相关性阈值
    enable_compression: bool = True  # 启用压缩
    
    def get_available_tokens(self) -> int:
        return int(self.max_tokens * (1 - self.reserve_ratio))
        # 8000 * 0.85 = 6800 tokens 可用
```

### 9.4.7 使用示例

```python
from context.builder import ContextBuilder, ContextConfig

# 初始化
builder = ContextBuilder(
    memory_tool=memory_tool,
    rag_tool=rag_tool,
    config=ContextConfig(max_tokens=8000)
)

# 构建上下文
context = builder.build(
    user_query="优化登录性能",
    conversation_history=messages,
    system_instructions="你是代码助手"
)

# 直接用作 LLM prompt
response = llm.chat(context)
```

## 9.5 上下文检索与智能体式搜索

### 9.5.1 智能体的定义

> **智能体 = 在循环中自主调用工具的 LLM**

随着底层模型能力增强，智能体的自治水平可提升：能独立探索复杂问题空间，并从错误中恢复。

### 9.5.2 从静态检索到及时(JIT)上下文

| 传统方式 | 智能体方式 |
|---------|-----------|
| 预先一次性检索(embedding)加载所有相关数据 | 运行时通过工具**动态按需加载** |
| 把整块数据塞入上下文 | **轻量化引用**（文件路径、URL等） |

**好处**：不用死记硬背全部信息，而是像人用文件系统、收件箱、书签一样**按需提取**。

### 9.5.3 元数据的价值

引用的元数据本身能帮助精炼行为：
- 目录层级、命名约定、时间戳都隐含"目的与时效"
- 例如 `tests/test_utils.py` vs `src/core/test_utils.py` 语义暗示就不同

### 9.5.4 渐进式披露 (Progressive Disclosure)

每一步交互都会产生新的上下文，反过来指导下一步决策：
- 文件大小暗示复杂度
- 命名暗示用途
- 时间戳暗示相关性

智能体得以按层构建理解，只在工作记忆中保留"当前必要子集"，并用"记笔记"的方式做补充持久化，从而维持聚焦而非"被大而全拖垮"。

### 9.5.5 混合策略

在实践中，**混合策略**更有效：

1. **前置加载**少量"高价值"上下文以保证速度
   - 例如：预先放入 README、项目约定说明
   
2. **允许智能体按需继续自主探索**
   - 提供 `glob`、`grep` 等工具让智能体即时检索具体文件
   - 从而绕开过时索引与复杂语法法树的泥沼

边界的选择取决于任务动态性与时效要求。

---

## 9.6 核心要点总结

1. **上下文是稀缺资源** — 不要浪费在无关信息上
2. **上下文腐蚀是真实存在的** — 越长不一定越好
3. **动态优于静态** — JIT 按需加载优于一次性全塞
4. **元数据有价值** — 文件名、路径、时间戳都是有用信号
5. **渐进式披露** — 边做边查，保持工作记忆精简
6. **混合策略** — 预加载核心 + 动态检索细节

**有意识的上下文工程是构建强健智能体的必需品。**

## 9.7 面向长时程任务的上下文工程

长时程任务要求智能体在超出上下文窗口的长序列行动中，仍能保持连贯性。上下文一致与目标导向，例如大型代码库、跨数小时的系统性研究、指导无限大上下文窗口并不能根治"上下文污染"与相关性退化的问题，因此需要具体策略。

### 9.7.1 三大核心策略

#### 1. 压缩整合 (Compaction)

**定义**：当对话接近上下文上限时，对其进行高保真总结，并用该摘要替换一个新的上下文窗口，以维持长连续性。

**实践方法**：
- 让模型压缩并保留关键信息：未解决挑战、实现细节，丢弃重复的工具输出与噪声
- 新窗口携带压缩摘要 + 最近少量高相关工件（如"最近访问的若干文件"）

**调参建议**：
- 先优化**召回**（缩减不遗漏关键信息）
- 再优化**精确度**（删除冗余内容）
- 一种安全的"轻触式"压缩策略对深层中的工具调用与清理

#### 2. 结构化笔记 (Structured note-taking)

**定义**：智能体以固定频率将关键信息写入**上下文外的持久化存储**，在后续阶段按需调回。

**价值**：
- 以较低的上下文开销维持持久状态与依赖关系
- 例如维护 TODO 列表、项目 NOTES.md、关键结论/依赖/思考的索引
- 跨数十次工具调用与多轮上下文重置仍能保持连续性

**应用场景**：
- 在非编码场景中同样有效（如长期策略任务、游戏/仿真中的目标管理与统计计数）
- 结合第八章的 `MemoryTool`，可轻松实现文件式/问答式的外部记忆并在运行时检索

**与 LangGraph State 的关系**：
- **LangGraph State** = 内存结构化存储（短期工作记忆）
- **外部文件/向量库** = 持久化存储（长期知识）
- 两者结合：State 存当前任务和最近步骤，外部存项目文档和历史决策

```python
# LangGraph State 示例
from typing import TypedDict, Annotated
from langgraph.graph import add_messages

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]  # 对话历史
    current_task: str                         # 当前任务
    completed_steps: list[str]                # 已完成步骤
    notes: dict                               # 结构化笔记
    artifacts: list[str]                      # 生成的工件
```

#### 3. 子代理架构 (Sub-agent architectures)

**思想**：由主代理负责层级规划与统合，多个专长子代理在"干净的上下文窗口"中各自深挖。

**好处**：
- **关注点分离**：成员的视界上下文窗口子代理内部，主代理专注于整合与推进
- **并行探索**：适合需要并行探索的复杂研究/分析任务

**经验**：
- 公开的多智能体研究系统显示，这模式在复杂研究任务上相比轻省代理基线有显著优势
- 常见于 1,000-2,000 tokens 规模的子任务分解

### 9.7.2 方法取舍

| 策略 | 适用场景 | 核心优势 |
|------|---------|---------|
| **压缩整合** | 需要长对话连续性的任务 | 强调上下文的"核力"，适合需要长话题连贯性 |
| **结构化笔记** | 复杂维护/阶段性成果的迭代式开发与研究 | 适合复杂维护/阶段性成果的迭代式开发与研究 |
| **子代理架构** | 复杂研究与分析，能从并行探索中获益 | 适合复杂研究与分析，能从并行探索中获益 |

### 9.7.3 核心洞察

即便模型能力持续提升，**在长交互中维持适度性与紧凑性**的是构建强健智能体的核心挑战。这些策略提供的上下文工程将长期保持具关键价值。

**关键原则**：
- 不是"能塞多少塞多少"，而是"该塞什么才塞什么"
- 外部存储 + 按需检索 > 一次性全部加载
- 分层架构 + 职责分离 > 单体大上下文
